The principal weaknesses are inconsistent completion rules, inadequate validation of model output, and insufficient separation of assessment evidence, reference material, and durable learner characteristics.

1. **F-01 — High: one lesson has conflicting definitions of completion.**

   **Code / Synthetic.** The coach prompt says to announce achievement at progress 9–10, but the engine only transitions an active lesson to completed at 10. At 9, the UI computes 90%, retains the ordinary exemplar label, and withholds the completed-thread next-lesson control. This establishes a disagreement between chat instructions and application state; learner abandonment is a plausible consequence, not an observed rate.

   The 20-exchange directive compounds the problem: it permits progress 10 when the exemplar is demonstrated “or something close to it.” The prompt elevates `pacingDirective` to an instruction that overrides normal coaching, while code comments describe it as a nudge. The instruction to drop “non-essential objectives” also fails to identify which authored objectives, if any, are optional. There is no automatic exchange-count completion in code, but the prompt can lower the assessment standard.

   Recommended correction: define a single rule across prompt, runtime directives, and UI. At 9, name the missing evidence and request one focused next step. Award 10 and announce achievement only when required criteria are demonstrated. Pacing may simplify activities and remove optional exploration; it must not silently waive authored requirements. If an author intends optional objectives or equivalent evidence, represent that explicitly.

   Sources: [coach completion and pacing rules](/home/ubuntu/googleplato/client/prompts/coach.md:83), [runtime pacing](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:768), [completion transition](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:674), [progress display](/home/ubuntu/googleplato/client/src/components/chat/ProgressBar.jsx:9), [next-lesson control](/home/ubuntu/googleplato/client/src/pages/LessonChat.jsx:650).

2. **F-02 — High: output parsing can falsely complete lessons or silently lose updates, and the opening uses a different contract.**

   **Code / Synthetic.** The parser takes the first matching progress marker anywhere in a reply. A quoted `[PROGRESS: 10]` before a correct terminal `[PROGRESS: 6]` yields completion and truncates visible prose at the quotation. An out-of-range `[PROGRESS: 100]` becomes 10 during ordinary turn processing. Conversely, `[PROGRESS: 10/10]` and `[PROGRESS: 8.5]` produce no score. Malformed JSON is silently ignored; a fenced reply leaves an opening code fence visible after the tags are stripped.

   The opening directly assigns the parsed score without normal-turn validation. A mocked call through `startLesson` stored progress 100 with status `active`. The opening also discards its parsed knowledge-base and profile updates. These are application-contract failures; they do not establish how often a live model emits such output.

   Recommended correction: define one validated terminal metadata section for opening, active, and completed turns. Require one integer score in 0–10, reject duplicate or contradictory control sections, validate update shapes, and preserve valid prior state when metadata fails. A malformed score must not award completion. Define an opening score policy and prevent unearned opening completion. Either apply valid opening observations or explicitly instruct the opening not to emit them. For completed threads, consistently repeat the frozen 10 or define an explicit omission rule; repeating 10 for this lesson does not itself violate the prohibition on assessing another lesson.

   Sources: [parser and display stripping](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:103), [opening handling](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:324), [normal-turn score handling](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:628), [response contract](/home/ubuntu/googleplato/client/prompts/coach.md:121).

3. **F-03 — Medium: the author’s objectives and assessment criteria are not reliably preserved during initialization.**

   **Code / Synthetic.** The Lesson Owner regenerates objective/evidence pairs for each learner. The prompt requires the exemplar to be echoed verbatim, but does not impose equivalent preservation on objective text. Validation checks shape and a nonempty objective list, not correspondence to the author’s objectives. The coach subsequently receives the generated objectives without the original list for comparison. A real orchestration call with mocked output accepted one generated objective for a lesson containing two authored objectives.

   The Lesson Owner does not receive `coachDirective`, although the authoring contract uses that field to preserve rubrics and scenario-specific assessment requirements. In addition, `callWithValidation` returns the second response even when it still fails non-safety validation. A new probe confirmed acceptance of an empty objective list after two failed validation attempts.

   Recommended correction: keep authored objectives as authoritative records with stable identifiers; generate evidence definitions alongside them; validate complete, nonduplicated coverage. Supply any author-defined assessment criteria to the initializer. Personalize examples and support while preserving requirements. Invalid initialization must yield a recoverable failure or a clearly defined safe fallback, rather than an unusable assessment state. Evidence definitions should be concrete enough to distinguish adequate from inadequate work; word-count and exchange-count targets must not erase the rubric.

   Sources: [Lesson Owner contract](/home/ubuntu/googleplato/client/prompts/lesson-owner.md:14), [initializer inputs](/home/ubuntu/googleplato/client/js/orchestrator.js:171), [validation retry](/home/ubuntu/googleplato/client/js/orchestrator.js:83), [validator](/home/ubuntu/googleplato/client/js/validators.js:15), [coach context](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:713), [authoring extraction contract](/home/ubuntu/googleplato/client/prompts/lesson-creator.md:36).

4. **F-04 — Medium: evidence disappears across turns while general observations grow without a real bound.**

   **Code / Synthetic.** Images and fetched page text reach the model only on the submission turn. Later history contains learner text or `[image]` / `[link]` placeholders; attachment metadata is excluded from the model’s conversation tail. The prompt nevertheless asks the coach to confirm that a linked page is the learner’s finished submission. In the original review’s two-turn mocked reproduction, the confirmation request contained neither the page evidence nor its URL. Text history is limited to 40 messages, so earlier text evidence can also leave the conversation window.

   The knowledge-base prompt does not require source-specific observations or per-objective evidence records. Meanwhile, its observation pruning preserves older text by recursively wrapping it in an `Earlier` item. With two short observations per exchange, the new probe produced 20 nested wrappers at exchange 25 and 95 at exchange 100; the serialized observations grew from 1,514 to 6,241 characters. Array length stays small, but old text is not actually discarded or distilled.

   Recommended correction: retain a bounded evidence record for each objective, including the relevant submission or source identifier, what was actually visible, and whether submission ownership/finality is confirmed. Confirmation alone must not establish quality. Make needed artifacts available again, or retain enough explicit observations to assess them without pretending to reread them. Bound general observations separately by size and replace or distill older summaries rather than nesting them. Preserve valid assessment evidence when ordinary history is shortened.

   Sources: [attachment instructions](/home/ubuntu/googleplato/client/prompts/coach.md:100), [attachment assembly](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:370), [history window](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:424), [persisted attachment representation](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:457), [observation accumulation](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:652).

5. **F-05 — Medium: the coach lacks an explicit policy for how different learner responses change the assessment.**

   **Code / Historical / Inference.** The prompt does tell the coach to evaluate substantive work against the exemplar and objectives. The gap is therefore not a total absence of objective-based assessment. It is the absence of a required mapping from observed evidence to each objective and then to the score. The broad progress descriptions and one sentence permitting score decreases leave retractions, contradictory evidence, ordinary uncertainty, and clarification requests underspecified.

   The historical model-selection document reports weak reassessment after a learner retracted earlier work. Those results support including retractions in an evaluation suite, but are not current-provider measurements and do not establish a universally correct replacement score.

   Recommended correction: distinguish submitted work, questions, clarification, uncertainty, corrections/retractions, lesson feedback, and requests to pause. Record what the learner demonstrated and the remaining gap before choosing a score or next step. Do not lower a score merely because the learner asks for help or struggles with a new requirement. Reassess when a retraction or misconception invalidates specific earlier evidence; retain other valid evidence instead of automatically resetting to 1–3. Accept equivalent demonstrations and preserve the existing safeguard against awarding mastery for agreement with the coach’s own answer.

   Add proportionate guidance for language preference, stopping or resuming, and distress: respect a request to pause, avoid pressuring the learner to finish, and use an appropriate supportive response when needed. These are missing behavior specifications, not observed incidents or justification for a broad new safety workflow.

   Sources: [assessment role](/home/ubuntu/googleplato/client/prompts/coach.md:49), [response flow](/home/ubuntu/googleplato/client/prompts/coach.md:83), [score and state descriptions](/home/ubuntu/googleplato/client/prompts/coach.md:127), [historical retraction evaluation](/home/ubuntu/googleplato/docs/MODEL_SELECTION.md:415).

6. **F-06 — Medium: routine lesson observations become compulsory profile rewrites, including after completion.**

   **Code / Synthetic / Inference.** On a successfully saved learner turn, a profile observation triggers an update; if it is absent, nonempty knowledge-base insights trigger the same update. Since the prompt requests one or two insights each response, normal compliant replies can cause an additional profile-model call even without an explicit profile tag. This includes completed-thread feedback. A mocked post-completion turn confirmed that a coach observation about confusing lesson instructions was passed to the profile updater as `learnerFeedback`.

   That prompt requires at least one changed field, says the latest evidence wins, and instructs the model to add confusion or inability to weaknesses. This can turn a temporary difficulty or criticism of lesson design into a durable learner trait. The broad instruction to record “ANYTHING” also lacks a relevance boundary for incidental sensitive disclosures; no actual disclosure or exposure was inspected here. Separately, `mergeProfile` preserves existing weaknesses when the model returns an empty list, preventing removal of the last obsolete weakness despite the completion prompt’s instruction to remove contradicted weaknesses.

   Recommended correction: stop treating all lesson insights as profile-worthy feedback; preserve who made an observation and its context; require useful, supported, durable information for profile updates; permit a validated no-change result. Keep lesson feedback and temporary difficulties in lesson state. Minimize incidental sensitive details, and support explicit clearing of obsolete profile facts. Removing the fallback alone does not resolve forced profile edits; relaxing the prompt alone does not remove extra calls. Both behavior and persistence semantics need a coherent contract.

   Sources: [profile-update triggers](/home/ubuntu/googleplato/client/src/lib/lessonEngine.js:478), [coach profile prompt](/home/ubuntu/googleplato/client/prompts/coach.md:147), [incremental profile rules](/home/ubuntu/googleplato/client/prompts/learner-profile-update.md:20), [observation handoff](/home/ubuntu/googleplato/client/src/lib/profileQueue.js:104), [merge behavior](/home/ubuntu/googleplato/client/src/lib/profileQueue.js:30), [completion-profile rules](/home/ubuntu/googleplato/client/prompts/learner-profile-owner.md:30).

7. **F-07 — Medium: the coach forbids external work that the authoring prompt permits.**

   **Code.** The coach is told not to ask learners to use external desktop applications or run code in a terminal. The authoring prompt distinguishes unavailable in-platform capabilities from supported submissions and explicitly permits creating a wireframe and uploading a screenshot. Those instructions conflict for lessons requiring work outside plato.

   Recommended correction: distinguish where work is performed from how evidence is submitted. Learners may use appropriate available external tools and submit text, supported images, or readable links; plato itself does not execute software or accept unsupported uploads. Preserve learner device and access constraints rather than promising that every tool is available. No change to supported input types is implied.

   Sources: [coach platform constraints](/home/ubuntu/googleplato/client/prompts/coach.md:33), [authoring platform constraints and examples](/home/ubuntu/googleplato/client/prompts/lesson-creator.md:63).

8. **F-08 — Medium: reference material needs an explicit instruction boundary, especially plugin enrichment.**

   **Code / Inference.** Attached pages are already labeled reference material and carry a no-unconfirmed-completion instruction. The additional reviews’ claim that they are wholly unmarked is too broad. However, there is no explicit rule rejecting instructions embedded in page contents, screenshots, or other reference material. `enrichmentContext` is injected into the current-state JSON but is missing from the coach prompt’s input definitions. Its non-authoritative status exists in a code comment, not in instructions the model receives.

   Recommended correction: document enrichment fields and their provenance; distinguish authored coaching directives from source content; state that instructions quoted inside reference material cannot change objectives, assessment, output format, or completion rules. Use supplied or verified resource links and acknowledge unavailable source content rather than inventing a URL. These are prompt and input-contract improvements; resistance to a particular injection or frequency of fabricated links remains untested.
