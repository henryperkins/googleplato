# PR #3 review and fixes

Review target: [PR #3](https://github.com/henryperkins/googleplato/pull/3), initially
`91d194e..ce25f22`. The review covered PostgreSQL adapter compatibility, lesson
transactions and reset fencing, startup, shutdown, container configuration,
tests, documentation, and existing automated review comments.

## Findings and changes

- **Concurrent startup failure (P2):** two instances updating an existing bundled
  prompt could read the same version. One write succeeded; the other caused
  startup to exit on a version conflict. This was reproduced against PostgreSQL
  17. Seeding now retries only conditional conflicts, rereading content each time,
  with three total attempts. Other errors and persistent conflicts still fail.
- **Validation gap:** test/lint workflows pointed at nonexistent workspace
  lockfiles, and the PostgreSQL tests lacked a database. Both workflows now use
  Node 24 and the root lockfile; tests receive a PostgreSQL 17 service.
- **Runtime hardening:** startup removes the bootstrap password before config
  imports and plugin loading, on both initial and subsequent starts. It does not
  reset an existing operator's password. Shutdown drains requests, handles
  cleanup errors without logging connection details, and enforces an eight-second
  deadline. The database pool is private, and connector cleanup uses `finally`.
- **Adapter hardening:** refresh lookups require refresh tokens rather than
  accepting password-reset records. Ordered query helpers take explicit constant
  ordering clauses. These do not change lesson persistence semantics.

The reset-generation concern in the automated review was not a defect: stale
turns are fenced by a fresh UUID value, independent of the marker row's numeric
version. A regression now covers repeated resets. The suggestion to retry
PostgreSQL `42501` was declined: this means insufficient privilege and remains a
fatal startup error. The earlier ordered queries were valid SQL; separating the
ordering argument is a clarity improvement, not a repaired injection flaw.

## Validation

After a clean `npm ci` on Node 24:

```sh
POSTGRES_TEST_URL=postgres://postgres@127.0.0.1:55433/postgres npm test
npm run lint
npm run build:client
git diff --check
```

- **891 tests passed:** 350 client and 541 server; zero failures or skips.
- The new PostgreSQL regressions exercise concurrent real seed operations,
  bounded conflicts, permission-error propagation, password handling on clean
  and existing databases, and reset-token rejection.
- Shutdown subprocess tests use real HTTP requests to check draining, failed
  cleanup, open streams, and stalled database cleanup.
- Lint: zero errors; 21 existing warnings in unchanged client files. Build and
  diff checks passed. Both modified workflow files parsed successfully as YAML.
- An independent agent reviewed the original PR, reproduced the startup race,
  reviewed the final patch, and independently passed all 15 focused PostgreSQL,
  startup and shutdown tests. Its final verdict was ready to merge with no
  remaining findings, conditional on the full validation above succeeding.
- Hosted Actions remained blocked before execution by the GitHub account billing
  lock. The [run annotation](https://github.com/henryperkins/googleplato/actions/runs/39516936470)
  confirms the external blocker. These local results are not hosted CI results.

The review used the isolated `fix/cloud-run-durable-storage` worktree. A private
baseline records the original checkout's 750 file hashes, index, HEAD and dirty
status for preservation checks. Only PR-related files are included in the fix.
Concurrent AI-settings/OAuth work appeared in the original checkout during the
review and was excluded. The merge leaves that active checkout's branch and
files in place rather than fast-forwarding it underneath the other work.

This review qualifies the source and local behavior. The earlier live Cloud Run
replacement and persistence-only retry evidence is recorded separately in
[the deployment record](cloud-run-durability-2026-10-20.md); these review fixes
require a later application deployment to take effect there.
