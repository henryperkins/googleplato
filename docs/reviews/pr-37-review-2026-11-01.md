**A learner who returns during a save retry now receives its completed result, and a memory-only draft activates the existing reload guard.** Review follow-up for [PR #37](https://github.com/henryperkins/googleplato/pull/37). The original publication was `507ac31`; `49bfaf6` added two failure-boundary tests. A subsequent independent review found the two navigation/recovery gaps below. Both were reproduced against the original build, corrected, and verified with the complete learner browser suite.

**F-03 · P2 — Reopening during Retry saving could leave a successfully saved lesson blocked. Fixed.** Fail the first save, start a held retry, return to Lessons, reopen the lesson, then release the retry. Before the fix, `retryLessonSave` ran outside `submissionRequests`; `resumeLesson` returned an obsolete pending snapshot, while the unmounted view ignored the late success. The learner could see Retry saving after the journal had already cleared, leaving Send blocked. Expected: the reopened view joins the same account/lesson request and receives its eventual success or supported failure. The smallest fix registers persistence-only retries in the existing request map and clears them on settlement. The new browser cases cover both retry success and retry failure, preserve the newer draft, assert one coach call and one committed response, and verify an enabled Send without another reload. Both cases failed before the fix and pass in Chromium and WebKit. Next check: repeat navigation and interruption on the devices reserved by C-B5-D01/D02 using the final build.

**F-04 · P2 — Failed draft retention did not activate the existing unload guard. Fixed.** Exhaust native sessionStorage, enter a newer nonempty draft, then dispatch a cancelable beforeunload event. Before the fix, the event was not canceled because the effect only considered pending server saves and active loading. The newer draft existed only in memory, so an accidental reload could discard it without the existing guard. Expected: failed retention activates that guard until verified retention succeeds. The smallest fix adds the failed, nonempty draft condition to the effect and its dependencies. The extended native-quota browser case failed before the fix and now verifies guard activation and removal after retry in both engines. This proves handler behavior, not a native mobile prompt. Next check: browser reload/back behavior in C-B5-D01/D02; OS termination and tab discard remain outside the guarantee.

**Review concerns without a confirmed implementation defect:**

| Review concern | Verified condition and disposition |
|---|---|
| Draft writes could overlap and publish stale retention status | `lessonDrafts.write` uses synchronous sessionStorage calls without an asynchronous boundary. It updates the entry before notifying subscribers; subscribers read the current map entry. The proposed asynchronous storage interleaving does not occur with the supported storage implementation. Existing native-quota, ignored-write, rapid editing and reload checks remain applicable. No implementation defect confirmed. |
| A rejected save retry could remain in `saving` | `persistLessonTurn` catches network, HTTP, timeout and acknowledgment errors and returns a retryable persistence result. `retryLessonSave` then finishes the submission. New browser coverage rejects a retry at the network boundary and verifies that saving ends, Retry saving remains enabled, and a later attempt succeeds. No implementation defect confirmed. |
| A response without `lessonKB` could crash the optional chain | `requestState` validates the response before exposing a saved state. Missing `lessonKB` is rejected as `invalid_ack`. New browser coverage commits the real local transaction, removes `lessonKB` from its acknowledgment, and verifies the failure notice and a successful idempotent retry. No implementation defect confirmed. |
| Unbound subscription method could be unsafe | The reviewer explicitly retracted this comment. The function has stable identity and uses the closed-over listener set, not `this`. No change needed. |

**Recommendations and limits remain separate from defects.** The external review also proposed persisting a stale-draft marker. The existing inline warning explicitly instructs the learner to keep the tab open and retry or copy their work. When storage is full, blocked or silently discarding writes, an additional durable marker cannot be guaranteed. The fix preserves the last verified draft rather than deleting that checkpoint to create space. If the learner discards the warning, or the OS terminates the tab, newer memory-only edits and the memory-only failure status can still be lost. A broader durability design is a separate recommendation; F-04 reduces supported accidental reloads without promising protection from native mobile lifecycle behavior.
